## 1. 원인 분리 (무엇이 아니고 무엇인가)

| 가설 | 검사 | 결과 |
|---|---|---|
| 학습 템플릿과 서빙 템플릿 불일치 | 같은 메시지를 HF `apply_chat_template`과 llama.cpp `/apply-template`(pilot GGUF, 사이트 GGUF)로 렌더링했다 | **문자열과 토큰 371개 모두 동일. 원인 아님** |
| 사고 모드 접두어 누락 | 57행 렌더링 | 57/57에 `<think>\n\n</think>\n\n`이 있음 |
| 정답 마스크와 EOS | 프롬프트는 -100, 정답 뒤에 `<|im_end|>`(151645)를 붙여 학습. 프롬프트와 정답을 따로 토큰화한 결과 = 이어 붙여 토큰화한 결과 | 57/57 동일, 57/57이 EOS로 끝남. padding은 `<|endoftext|>`이고 마스크로 제외. packing 없음 |
| LoRA 감싸기·병합 경로 자체의 변형 | 학습하지 않은 LoRA(B=0)와 그 병합본의 logit을 원본과 비교(3행, MPS bf16) | 최대 차이 **0.0 / 0.0** (`model-repair-001/zero-update.json`) |
| 최적화·마스크·EOS가 학습을 막음 | 같은 학습 코드와 설정(LoRA r16, lr 2e-4)으로 짧은 정상 6행을 40단계 과적합 | 손실 3.07 → 0.0003. 6/6행을 **글자 그대로 재현하고 EOS에서 멈춤** (`overfit-short6.json`, 484초). **학습 경로 정상** |
| **학습 데이터 계약** | train 57행 집계 (`train57-contract.json`) | **원인.** 아래 표 |

**train57의 문제:**

| 항목 | 값 |
|---|---|
| 사용자 턴 지시 | "답에 출처 번호를 붙이세요", "근거가 없으면 확인 불가"(`RAG_PREFIX`) + CASE_SYSTEM "결론·이유·조건·예외를 빠짐없이" |
| [Dn] 출처 번호가 있는 정답 | **0/57** |
| 정답 길이(토큰) | 중앙값 711, p90 1,448, 최대 1,791. 256 초과 36행, 512 초과 31행 |
| 원문 복사 | 30자 이상 구간이 근거 원문과 같은 비율은 평균 50%, 문장의 44.6%가 원문 그대로 |
| 과제 편중 | `official_answer_extraction` 31행이 답 토큰의 **89.1%**를 차지하고 원문 복사율 90%, 중앙값 1,215토큰. 표·조문·코드 행은 복사 0, 91~159토큰 |
| 학습량 | 114행(2 epoch), 15단계, lr 2e-4 |

- **결론:**
  - 학습 경로는 정상이다. 모델은 **배운 그대로** 행동했다. 근거 원문을 길게 옮기고, 출처 번호를 달지 않고, 짧은 형식 지시를 무시했다.
  - 그 결과 C-024의 증상이 나왔다:
    - 64토큰 잘림이 58 → 255건으로 늘었다.
    - content_strict는 98 → 1로 떨어졌다.
    - 프롬프트 복사가 2 → 9/14로 늘었다.
  - C-023에서는 512토큰을 허용해도 9 → 2였다. 그러니 출력 한도 탓만은 아니다. 지시와 정답이 어긋난 데이터를 학습한 것이 주원인이다.
  - 표 정답이 근거에 없는 수집일을 말하는 문제도 있었다(B 확인).

## 2. 계약 수정
- **B (생성기, 커밋 `9f8f218`, `MODEL-REPAIR-001-B.md`):** `data/case-training-view-v1`을 만들었다.
  - 문장마다 `[Dn]` 출처 번호를 단다. 근거가 없는 행은 `확인 불가: `로 시작한다.
  - D1 앞에 `자료 정보: 문서·기관·기준 시점` 줄을 붙인다.
  - 답 256토큰과 문맥 4,096토큰 한도를 넘는 행은 버리지 않고 보류한다.
  - 결과: train 34, dev 6. 원본 정답과 되돌려 대조할 수 있다.
- **A (소비자, `scripts/train_open_weight_lora.py`):** `case` 행이 계약을 어기면 그 id를 대며 **학습을 멈춘다**(조용히 버리지 않음). 어김의 기준:
  - `[Dn]`도 없고 `확인 불가: `로 시작하지도 않는 경우
  - 없는 근거 번호를 인용한 경우
  - 정답이 `--max-answer-tokens`(기본 256, EOS 포함)를 넘는 경우
- **양쪽 확인 결과:**
  - case-view-v1 40행: 위반 0, 최대 252토큰
  - 기존 train57: 57행 모두 `no_citation`이라 다시 학습할 수 없다
- **진단 도구:** `scripts/diagnose_lora_pipeline.py`. 학습기의 `load_rows`, `encode`, `batch_loss`를 그대로 써서 zero-update와 소수 과적합을 검사한다.

## 3. 아직 하지 않은 것과 재학습 계획 (승인 필요)
- **재학습은 하지 않았다.** B가 지적했듯 v1은 34행(답 토큰 5,457)뿐이다. 2 epoch, batch 8이면 9단계다. 이 판으로 학습할지, 공식 해석 72행과 쉬운 설명 11행을 짧게 다시 쓴 판을 기다릴지는 총괄이 정한다.
- **실측 기반 비용:**
  - 같은 맥북 MPS에서 1.7B LoRA는 정답 100토큰대 행 1회 forward/backward에 약 2초가 걸렸다(과적합 실측).
  - v1 전체(68행 통과, 문맥 최대 4,096)는 약 5~10분으로 추정한다.
  - **GPU job이 필요 없다.** 새 비용 0원.
- **중단 조건:**
  - 손실이 유한하지 않음(학습기 내장)
  - 계약 위반(학습기 내장)
  - 5단계 뒤 예상 시간이 30분을 넘음(`--max-train-seconds 1800`)
- **평가 계약 (C 소유):** 원본과 재학습본을 **같은 근거, 같은 출력 계약**으로 비교한다.
  - 학습 형식: CASE_SYSTEM + rag_prompt, D1 앞의 `자료 정보:` 줄, 답 256토큰, 문장 끝 `[Dn]`, `확인 불가:`
  - 값 형식 평가(grammar_instructed, 64토큰)와 case 형식 평가를 섞지 않는다.
  - 값 형식이 회귀하는지는 별도 지표로 본다.
- **서빙 계약 (재학습본을 배포할 때 A가 할 일):**
  - case 모드 근거 D1 앞에 B와 같은 `자료 정보:` 줄을 붙인다. 문서명, 기관, `기준 일자 종류(이후 개정 여부 미확인)`이다.
  - 답 한도는 256토큰으로 맞춘다.
  - 해당 버전이 없어서 아직 서빙 코드는 바꾸지 않았다.
- **새 모델이 생긴 것처럼 주장하지 않는다.** 정확도 개선은 C의 matched 평가 뒤에만 말할 수 있다.
