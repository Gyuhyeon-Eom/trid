## 4. 사전 등록 (실행 전 고정)

**무엇을 보는 실험인가**
- 현재 SFT 레시피에서 학습 단계 수와 lr 스케줄을 함께 늘리면 정확도가 오르는지 본다.
- A-004 E1(3,600단계) 결과와 이어서 1,200 → 3,600 → 12,000 곡선을 만든다.
- 데이터(mix-04), batch 8, seed, 문맥, 평가 규칙은 바꾸지 않는다.

**보고 지표 (ACCURACY-FIRST-001)**

| 범주 | 지표 |
|---|---|
| 주지표 | RAG310 답 있음 엄격 정답 (evidence) |
| 보류·허위 응답 | 답 있는데 보류, 답 없는데 답함 |
| 답한 문항 기준 | 답한 문항 중 정답 비율 |
| 오류 유형 | 출처 맞고 값 틀림, 출처 틀림, 충돌 문항 오답 |
| 질문 이해 | KLUE dev 정답·질문 민감도 |
| 학습 곡선 | train / valid 손실 곡선 |

**과적합 노출량** (`reports/coordination/A-006/exposure-simulation.json`)
- 12,000단계: 행 기준 평균 5.2회, 공공문서 29행은 행당 약 166회
- 36,000단계: 행 기준 평균 15.5회

**S2 진행 조건 (S1 결과로 판단, 모두 충족)**
1. 390M 12,000이 같은 크기 A-003 1,200 대비 주지표 개선 문항이 악화 문항보다 많다(같은 문항 비교). 그리고 McNemar p<0.2다.
   - 이 기준은 다음 단계 탐색 여부를 정하는 데만 쓴다. 채택 관문이 아니다. 채택 관문은 기존 +5%p, p<0.05, 위험 회귀 제한 그대로다.
2. "답 없는데 답함"이 A-003 대비 5문항 넘게 늘지 않는다.
3. 검증 손실 선택 step이 12,000 근처다. 과적합으로 선택 step이 일찍 멈추지 않았다는 뜻이다.

- 하나라도 충족하지 못하면 S2를 쓰지 않고 예약을 반환한다.
- 체크포인트 선택은 검증 손실 규칙이다. 개발 점수가 가장 좋은 step을 최종 성능으로 제시하지 않는다.

**INTERNAL-WORKFLOW / ACCURACY-FIRST와의 관계**
- 이 실험은 **모델 단독 독해**만 본다. 내부 업무(DB/API·검색 결합), 권한, 시점 정합성은 측정하지 않는다.
- 기관 내부 데이터가 없으므로 해당 항목은 미검증으로 남는다.

## 5. 실행 방식

- **실행 경로:** A-006 재개 스모크에서 검증한 것을 쓴다.
  - `scripts/sm_sft_campaign.sh`: recovery 체크포인트, 마일스톤, 세그먼트 재개
  - `scripts/sm_eval_weights.sh`
  - 재개 검증 근거: 30만→60만이 아니라 300→600단계 분할 run이 한 번에 돌린 run과 검증 손실 차이 ≤5e-4. 분할 전 300단계에서도 이미 같은 크기의 차이가 있었다. CPU에서는 가중치가 비트 단위로 일치했다.
- **드라이버:** 자동 연결 드라이버는 쓰지 않는다. 각 job을 수동으로 한 번만 기동한다.
- **기록:** job별 시작·종료·Billable 초를 `reports/coordination/sm-jobs-A.jsonl`과 정산 보고에 남긴다.
- **비용 초과 기준:** 실행 중 누적 Billable × 단가가 예약 상한의 80%를 넘으면 저장 후 멈추고 보고한다.
