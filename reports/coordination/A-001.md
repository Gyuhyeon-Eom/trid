### 2.2 가설 (단정하지 않는다)

- **H1 (크기):** 같은 데이터·토큰·학습 절차에서 파라미터를 약 4배로 늘리면, 근거 제공 독해(RAG310 답 있음, KLUE dev)가 91M보다 좋아진다.
- **H2 (구조):** 같은 크기에서 GQA(16/4)와 QK-norm은 독해 성능을 해치지 않으면서 CPU KV 캐시를 줄인다.
- **대안 설명** (이번 실험으로 배제하지 않는다):
  - **사전학습 토큰 수:** 91M은 11억 토큰을 학습했다. 1B 토큰 파일럿에서는 91M과 350M이 같은 토큰을 본다.
  - **데이터 영역:** 웹 텍스트를 추가하는 효과는 크기와 분리해야 한다(3.2절 arm S91-v4).
  - **토크나이저:** 8,192 BPE로 한국어 약 1.76자/토큰이다. 문맥 1,024에 들어가는 글자 수가 제한된다. 이번 파일럿에서는 고정하고, 별도 실험으로 둔다.
  - **SFT 레시피와 평가 형식:** 모든 arm에 같은 SFT와 같은 평가를 적용해 상수로 둔다.
- **20 tokens/parameter:** 계획 휴리스틱일 뿐이다. 최소 필요량의 법칙으로 쓰지 않는다. 파일럿에서는 모든 arm의 토큰 수를 같게 두고, 확대 판단은 측정값으로 한다.

## 4. 중단·확대 기준 (실행 전 제안, 수치 확정은 총괄)

### 4.1 즉시 중단 (arm 단위)

1. 손실이 NaN이나 무한대가 되거나, 검증 손실이 직전 평가보다 0.5 이상 오른 상태가 평가 2회 연속 이어진다.
2. 측정 처리량이 3.3절 추정의 50% 미만이다. 원인(compile, 배치, I/O)을 진단하기 전까지 진행하지 않는다.
3. 같은 토큰 시점에서 S350의 검증 손실이 S91-v4보다 낮지 않다. 3억 토큰 이후 평가 3회 연속 이 상태면 최적화나 구현 문제로 보고 중단한다. 같은 데이터·토큰에서 큰 모델의 손실이 낮지 않다면 학습 설정을 먼저 의심해야 한다.

### 4.2 판정 (파일럿 1B 토큰 + 동일 SFT 후, 기준선은 S91-v4)

- **확대 조건 (전부 충족):**
  - RAG310 답 있음(evidence, 출처 일치 + 정답 언급)에서 S350이 S91-v4보다 많이 맞힌다. 같은 문항 McNemar 정확검정 p<0.05.
  - KLUE dev 정답 수가 S91-v4보다 많다.
  - "답 있는데 보류"와 "답 없는데 답함"이 각각 S91-v4보다 5문항 넘게 악화되지 않는다.
- **그다음 단계:** 선택한 350M arm을 더 큰 토큰 예산으로 학습한다. 토큰 예산은 파일럿 손실 곡선과 웹 데이터 반복 여부를 보고 총괄과 정한다. 고정 휴리스틱을 쓰지 않는다.
- **기각 조건:** 손실은 낮아졌는데 하류 평가가 개선되지 않는다. 이 경우 크기 가설을 기각하고, 남은 대안(토크나이저, SFT 데이터 구성, 추출 헤드)으로 넘어간다.
- 개선과 악화 문항 목록을 함께 보고한다. 총괄이 정한 합격선은 결과를 본 뒤 바꾸지 않는다.

## 6. 제안: 단일 raw → clean → tokens 계약

### 6.1 raw (소유 B)
- 위치: `s3://trid-training-148761639313/corpus/raw/<source>/`
- 원본을 바꾸지 않는다. HF는 revision을 고정하고 원본 바이트를 그대로 둔다.

### 6.2 clean (소유 B)
- 위치: `corpus/clean/<source>/<clean_version>/docs-*.jsonl.gz`
- 버전 디렉터리를 추가하자는 제안이다. 지금 B 경로에는 버전이 없다.
- 행 스키마는 B의 corpus contract를 그대로 쓴다. 다만 아래 필드가 **반드시** 있어야 한다.
  - `id`: 전체 출처에 걸쳐 유일
  - `group`: 문서 단위 분할 키
  - `kind`: 출처 안의 세부 유형
  - `text`: NFC, 비어 있지 않음, trid SPECIAL 토큰 없음
  - `sha256`: `text`의 해시
  - `license`, `attribution`, `source`
  - `split`: `train|valid|test`. 신규 필드다. B가 `group` 해시로 정한다(`build_pretraining_mix.split_for_group` 규칙). 같은 group이 여러 split에 걸치면 안 된다.
  - `filters`: 적용한 정제 버전 문자열. 신규 필드다.
- clean 단계에서 B가 보장할 것:
  1. `trid.korean_quality`의 `clean_lines`, 문자 비율 검사, `redact`(PII)
  2. 출처 내부 exact/near 중복 제거(공공 출처)
  3. 행 단위 사용권 기록
- FineWeb-2는 업스트림 품질 필터를 그대로 인정하고, 위 1~3만 추가한다.
- A 쪽 정제 함수와 결과가 같아야 한다. 같은 함수를 import해서 쓰면 된다.
- 샤드 manifest: `corpus/state/<source>/<clean_version>/manifest.json`에 샤드 키, sha256, 행 수, 글자 수, split별 집계를 기록한다. 완료 표식이 있는 버전만 A가 소비한다.

### 6.3 평가 오염 제거 (경계)
- 위치는 tokens 단계(A)다. 비공개 평가 정답이 학습 담당에게 노출되지 않게 하려는 것이다.
- 총괄(또는 평가 담당)이 평가 텍스트의 **단어 8-gram 64비트 해시 목록**만 `s3://…/eval-guard/<version>/ngrams.u64`로 제공한다.
- A는 해시와 겹치는 문서를 제외하고 제외 건수만 기록한다. 개발용 공개 평가(RAG310, KLUE dev 등)도 같은 방식으로 합친다.

### 6.4 tokens (소유 A)
- 입력: 위 clean manifest 목록 + eval-guard 해시 + 고정 토크나이저(sha256)
- 출력: `s3://…/tokens/<mix_version>/`
  - `train|valid|test.bin`: uint16, 문서마다 `<|bos|> text <|eos|>`
  - `manifest.json`: 입력 manifest sha256, 출처별 토큰 수, 제외 건수, 토크나이저 sha256
  - `sources.json`: kind는 `<source>:<kind>`, 문서 시작 offset 포함
- 출처별 토큰 예산은 결정적 해시 우선순위로 표본을 뽑는다. 업샘플링은 하지 않고, 반복은 학습 단계의 `source_weights`로만 한다.
- 출처 간 exact 중복 제거(공공 우선)는 tokens 단계에서 한 번 더 한다(NFC + 공백 제거 해시).

### 6.5 기존 코드 처리 (삭제 안 함, 총괄 승인 후)
- A의 `prepare_fineweb2_ko.py`에서 다운로드와 정제 부분은 B의 clean 단계로 넘긴다. A 쪽에는 clean manifest를 읽어 토큰화하는 `scripts/build_pretraining_tokens.py`를 새로 만든다.
- 그때까지 `prepare_fineweb2_ko.py`는 스모크용 참조 구현으로 남긴다.

## 7. 자원·할당량 (AWS-APPROVAL-001 범위)

- **EC2 서울 리전 G 계열 온디맨드:** 4 vCPU이며 C 인스턴스가 모두 쓰고 있다. 증가 요청(→8) `7b146fb9…` CASE_OPENED.
- **EC2 서울 리전 G 계열 스팟:** 0이다. 이번에 증가 요청(→16) `5fdf51d0…` PENDING을 제출했다.
- **다른 리전:** EC2 G/P 온디맨드·스팟이 모두 0이다(ap-northeast-1, us-east-1, us-west-2 확인).
- **즉시 쓸 수 있는 대안:** SageMaker 학습 작업 할당량이 EC2와 별도로 있다. 서울 리전에서 ml.g6e.xlarge, 2xlarge, 4xlarge, 8xlarge, 12xlarge(L40S 4장), 16xlarge가 각 1개다.
